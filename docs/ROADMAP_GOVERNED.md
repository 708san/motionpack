# Governed MotionPack roadmap

Targets are exploratory, not release commitments. This plan is reconciled with `main` after PR #130 (2026-11-12). Update its evidence links as implementation and CI change.

## Phase A — stabilize the experimental baseline

1. **Completed in PR #50:** obtain a successful isolated-reader matrix run and retain the run URL and per-OS test results. The successful main run is #175. If a later run fails, diagnose its actual job log before changing code.
2. Keep Issue #4 open. Resolve its remaining acceptance items in small changes with adversarial regression tests and independent security review. PR #91 removes archive-controlled asset paths from the host filesystem boundary during temporary validation staging. PR #95 adds bounded black-box mutation testing for the isolated Pillow raster decoder; its CI also passes the full Python suite (176 tests, 14 skipped) and the isolated-reader matrix on Linux, macOS, and Windows. Neither PR resolves path races, memory containment gaps, SVG renderer limits, private source handling, or browser-native decoder exposure. The strict secret scan is heuristic and does not establish the absence of secrets. Track the remaining gaps separately.
3. **Updated in PR #57:** keep frozen regression fixtures with pinned SHA-256 checks and direct/isolated reader tests for v0.1–v0.4; run the current functional, negative, isolated-process, visual and performance-report checks.

**Exit evidence:** green required checks on a named commit; no unsupported claim of a complete sandbox or browser decoder isolation.

## Phase B — define runtime and compatibility contracts

1. Extract a stateless pose evaluator that accepts a manifest, clip, variant, and millisecond timestamp; preserve generated preview behavior through the existing `window.MotionPackPlayer` facade. **PR #38 merged into main as `d3e1e37`.**
2. Define the host-driven lifecycle controller contract and keep it experimental until it has been exercised and accepted. The prototype was added in PR #39 and integrated into the generated preview facade in PR #40; the controller is not yet a stable public API.
3. Review the proposed [v1.0 compatibility policy](COMPATIBILITY_POLICY_DRAFT.md) before stabilizing format or runtime APIs. Manage file-format, runtime and authoring-tool versions separately; document required/optional capabilities, migration, deprecation, unsupported-feature errors and fallback export. The read-only legacy snapshot direction and initial migration handling policies are approved: sparse values remain separate from provenance-bearing effective values, ambiguous data is preserved/warned/uninterpreted, and lossy saves require prior confirmation. PR #79, #82, #84, #86 and #88 implement provenance-bearing effective defaults for documented omitted clip loop, v0.2+ IK weight, observed v0.2+ IK bend, v0.4 interaction flags, and burst count, without materializing them into source data. PR #99 records source-side evidence separately from those defaults and capability facts. The normalized view remains experimental; v1 meaning for IK and renderer/host support remain open. The experimental `report.migration_findings` ledger records confirmed mappings into that projection, v0.1 IK as preserved/uninterpreted, and unsupported top-level fields; it neither classifies every nested unknown nor assigns v1 meaning. PR #112 adds a separate bounded capability preflight prototype, not a reader integration. Public report/schema decisions, detailed v1.0 semantics, serializer and conversion behavior remain open. PR #130 merges the explicitly non-normative [v1 contract proposal](V1_CONTRACT_PROPOSAL.md); the core-shape, SVG-dimensions and canonicalization choices remain pending in Issue #120.
4. Keep v0.1–v0.4 experimental. Complete and review the [version-by-version feature inventory](V0_FEATURE_INVENTORY.md), then specify which non-ambiguous legacy fields/defaults and implementation behaviors map into v1.0; preserve and warn about ambiguous/spec-mismatch data without v1 semantic interpretation. Keep fixtures and compare sampled state and rendered output.

**Exit evidence:** accepted runtime API proposal, compatibility policy, versioned fixtures and acceptance criteria. Any public format change requires Architect review, migration notes and regression fixtures.

## Phase C — reusable playback and interaction

1. Build on the evaluator to add a host-owned player controller and rendering adapters. PR #39 added a DOM-free controller prototype with per-instance clip/variant/time state, play/pause/resume/stop/seek, state queries and disposal; PR #40 connected it to the generated preview while preserving the legacy facade. Loading/unloading, parameter updates, resizing and rendering adapters remain open.
2. The generated preview uses an experimental pointer-to-IK adapter: mouse and pen hover remain supported, primary touch tracks while pressed, and browser-native gestures remain enabled. The v0.4 adapter reports hover transitions, same-top-node touch taps, and mouse/pen or host-mapped keyboard clicks. Dragging, long press, and swipe remain open; keep host actions permissioned by the consuming application and never execute package JavaScript.
3. **Implemented experimentally in PR #47:** separate logical canvas size from viewport policy (contain, cover, stretch, alignment and high-DPI scaling). The default is centered contain; the adapter caps device-pixel ratio (DPR) at 2 and the backing bitmap at 16 million pixels and 8192 pixels per edge. The 91:55 ratio is a generic aspect-ratio test, not a product-specific feature. Browser-specific behavior and real-device verification remain open.
4. Add an offline export path only after the player API and asset lifecycle are stable.

**Exit evidence:** independent instances, deterministic virtual-time tests, accessibility alternatives, no network requests, and visual checks for representative ratios. Playwright device emulation must be reported separately from physical iOS/Android testing.

## Phase D — richer motion

Add independent X/Y scale, easing and squash/stretch, then explicit transitions and interruption rules. Preserve existing track meanings. Consider mesh deformation and blended rigs only after authoring and runtime contracts can represent and test them. Every renderer-visible change needs visual review; aesthetic quality still requires a human.

## Phase E — authoring foundation

Stabilize programmatic import, non-destructive source retention, masks/layer editing, rig setup, keyframe and clip operations, preview, validation and reproducible export. Keep source provenance separable and make edit/save/reload information-preservation testable. Build a GUI only on the stable authoring API.

## Phase F — optional AI authoring

After authoring APIs and quality evaluation are stable, prototype a model-independent workflow for planning, segmentation, motion generation, validation and iterative correction. Preserve originals and edit history; require explicit consent for network transfer. Keep AI optional and outside the v1.0 core unless a later scope decision demonstrates it is necessary. If v1.0 launch materials claim AI-assisted creation, require a reviewed end-to-end example that produces an editable package, retains original assets and provenance, supports human correction, and clearly identifies what information is sent off-device, when it is sent, and a non-AI workflow. Do not imply AI authoring is available until that evidence exists.

## Phase G — v1.0 release decision

Release only when maintainers approve all of the following:

- Stable format specification, capability profiles, extension rules and migration paths.
- Independent file, runtime and authoring-tool version policies and public API/deprecation rules.
- Frozen compatibility fixtures, read/write preservation checks, state comparisons and reviewed visual references.
- Security review of the reader, SVG/raster handling, process boundaries, dependency inventory and vulnerability contact/response process; documented residual risks.
- Supported-browser/device matrix backed by actual runs; performance budgets with repeatable thresholds; human visual and motion review of representative layered artwork and motion (composition, silhouette, palette and contrast, legibility at target sizes, layer editability, timing, motion naturalness and interaction feedback). Screenshot matching is regression evidence, not an art-quality verdict.
- Offline runtime, examples, docs, checksums/distribution artifacts and a maintainer-approved software license.

Do not require every exploratory capability (GUI, AI, mesh deformation, native engine adapters) for v1.0. Prefer a small stable core with explicit capability reporting over silent feature loss.
