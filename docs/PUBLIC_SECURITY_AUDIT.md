# Public pre-alpha security status

Basic path traversal checks, SVG subset validation, size budgets and negative metadata tests exist. These do not constitute a hardened security audit.

Unresolved (Issue #4):
- The reader checks at most 512 decompressed prefix bytes for common ZIP, gzip, bzip2, xz, 7-Zip, RAR, and tar headers on non-directory entries outside `source/`, including unreferenced entries. This bounded signature detection does not identify every archive variant or polyglot; `source/` remains opaque.
- The new experimental reader prechecks ZIP entry count and central-directory byte size, then checks paths, file types, duplicate/colliding names, declared sizes and compression ratios. Referenced assets are read with byte limits. PR #91 stages validation copies under generated names with allowlisted extensions, so ZIP-controlled path components (including host-special names) do not cross into the temporary host filesystem tree; returned manifest paths and asset bytes remain unchanged. This is a staging-boundary hardening, not a complete sandbox. The input path is checked for a regular-file target before open and the opened descriptor is checked afterward; `O_NONBLOCK` is used where exposed. `stat` and `open` are not atomic: a concurrently replaced path may still open a special file before descriptor rejection. On platforms without that flag that support blocking special-file types, a replacement after the initial check may block during open. Default `read_package()` now delegates parsing to `read_package_isolated()`; `read_package_in_process()` remains the explicit caller-process parser for trusted/local use and parser tooling. The isolated path snapshots inputs up to 40 MiB, applies a default 30-second (maximum 300-second) completion deadline and a 40 MiB response cap, kills/reaps its worker, and has a three-OS CI matrix. The deadline cannot interrupt synchronous process creation or OS job setup; that time is deducted once setup returns. Linux applies a 512 MiB per-worker address-space ceiling; Windows applies 512 MiB per-process and 512 MiB Job Object-wide committed-memory limits after the worker is assigned; macOS has no hard whole-process memory limit in this implementation. The wrapper is not a sandbox and does not make attacker-mutable source paths safe. Deterministic negative tests and bounded Atheris targets exercise ZIP reading, SVG validation, and PNG/JPEG/WebP header parsing (15 seconds per target on PRs, 300 seconds per target weekly/manual, 64 KiB maximum input); the raster target does not fuzz image decoders. The separate opt-in Pillow adapter now decodes static PNG/JPEG/WebP in a resource-limited child process, but is not a sandbox and is not used by the default offline preview. Animated WebP, SVG, full decoder fuzzing and the browser decoder remain unresolved. These finite campaigns do not provide continuous fuzzing. OS-specific containment and resource behavior remain limited by their documented mechanisms.
- The validator now rejects SVG attributes outside the documented per-element allowlists, in addition to its existing static-element and URL checks. Attribute values are not validated against every SVG value grammar. Complete SVG sanitization for arbitrary renderers, hostile raster media decoding and downstream renderer behavior remain unresolved. `.png`/`.jpg`/`.jpeg`/`.webp` asset paths receive format-specific header dimension checks before decode and share configured dimension/pixel limits. Animated WebP canvas and frame areas are counted, but frame image data is not decoded; JPEG DNL height remains unsupported, content under another extension is classified by that extension, the optional Pillow worker handles only static images, while the default preview still uses the browser decoder; neither path is a permission sandbox.
- The packager scans serialized manifest metadata (including referenced asset paths) and referenced-asset bytes for a small set of PEM private-key headers and GitHub/OpenAI/AWS credential-like patterns. Known matches are redacted from package diagnostics. By default it warns and still packages matching content; `--fail-on-secret-like` rejects matches before writing outputs. This best-effort scan can miss transformed or pixel-encoded secrets and can produce false positives; it does not certify an asset as safe. Comprehensive secret detection/filtering remains unresolved.
- Longer-running fuzzing, ongoing dependency review, stronger macOS memory isolation, complete sandboxing and resource-exhaustion defense beyond the wrapper's stated limits.

Untrusted packs must not be opened with a production assumption of safety.

## Independent Security Auditor review (2026-11-06)

A read-only review of the Issue #4 controls and negative-test definitions found no claim that the implementation is a complete sandbox. It identified three items for follow-up:

- The default `read_package()` API uses the isolated worker and its deadline, response cap, and platform-specific memory controls. `read_package_in_process()` remains available for explicit in-process use and has no process-level deadline or memory cap. Isolation is defense in depth only: the worker retains caller permissions, macOS has no hard whole-process memory limit, and process creation/OS setup cannot be interrupted by the deadline.
- The secret-like scanner previously covered referenced asset bytes but omitted the serialized manifest and asset paths, and validator errors could echo token-like values in invalid paths. This update extends scanning to those package metadata strings and redacts recognized patterns in packager errors while preserving warning-only default behavior and strict opt-in rejection. The heuristic remains incomplete.
- A possible mismatch between the Windows memory-limit test and worker error mapping was raised by static inspection. The Windows `isolated-reader-windows-2025` job passed in PR #27; the macOS job was canceled before setup and provides no test evidence.

The review was static and did not execute tests or fuzzing. See the repository CI evidence and test files for execution results; the review itself is not a formal certification.

## Scoped independent review (2026-11-12)

A Security Auditor reviewed PR #132’s Windows Job Object memory-limit change and found no defect in the added per-process plus job-wide committed-memory configuration. The test-only PR head reproduced the missing job-wide flag. The final Windows tests check the configured flag and value and verify that a child’s allocation is blocked when worker-plus-child committed memory exceeds the shared budget while each process remains below its per-process cap. Functional QA and Code Reviewer also reviewed that PR without blockers. Their review scope was this Windows memory-limit change, regression tests, and related documentation; it was not a full security certification or closure review of Issue #4. The actual test and workflow results are recorded above. Reviewers did not run tests locally.
